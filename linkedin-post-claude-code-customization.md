**Last week I argued junior developers shouldn't generate production code with AI.**

**This week I'm sharing how to customize Claude Code for maximum productivity.**

Contradiction? Not quite. Here's the nuance that gets lost in the AI debate:

The previous post wasn't anti-AI. It was about *how* you engage with these tools. The forklift vs. weightlifting analogy: using AI to skip the cognitive struggle that builds expertise is different from using AI to amplify expertise you've already built.

For junior developers, the risk is using AI as a thinking replacement—generating code you don't understand, shipping features while building no mental models, optimizing for output while accumulating capability debt.

For experienced developers, the calculus changes. You already have the foundation. You can evaluate AI output critically. You know what good solutions look like. The question becomes: how do you make these tools work harder for YOUR specific workflow?

That's what the new post covers—six mechanisms for customizing Claude Code:

→ Skills: Encode your project conventions so you stop re-explaining them every session
→ Subagents: Spawn parallel workers for code review, security scanning, test analysis
→ Slash Commands: Codify multi-step workflows you run repeatedly
→ MCP: Connect Claude to GitHub, databases, Kubernetes, internal tools
→ Plugins: Package configurations to share across teams
→ Hooks: Enforce standards automatically (formatting, linting, guardrails)

The common thread between both posts: intentionality.

Don't let AI do your thinking when you need to be building thinking capacity.
Do let AI handle repetitive work when you've already built the judgment to evaluate its output.

The goal isn't to use AI less or more. It's to use it *deliberately*—understanding what each mode of engagement builds versus what it atrophies.
